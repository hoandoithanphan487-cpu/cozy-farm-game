## 1. 为什么资源已经存在，游戏仍然很丑

仓库已有 N-006 的 131 张正式运行时像素 PNG、N-009 的 8 张高清角色立绘和 N-013 的 5 张高清建筑图，但当前运行页面仍主要由程序化色块、文字/符号、单体节点和调试字符串组成。根因不是“缺少图片文件”，而是以下运行时合同尚未建立完整：

1. `PixelAssetStore` 只认识少量资产种类，并没有覆盖 131 张正式资源。
2. `CharacterVisualNode` 的移动与动作主要是节点位移/缩放，不是对 4×4 spritesheet 的切帧播放。
3. 地图只有碰撞和少量地标坐标，没有草地变体、水边/水角、水动画、水渠方向、石路等视觉语义。
4. 建筑只有单格地标，没有五栋建筑的视觉锚点、占格、入口、遮挡和六层组合规则。
5. HUD 由一整段字符串拼接并逐行显示；它没有可独立布局的状态模型、工具栏、任务卡和反馈层。
6. 部分正式图片没有对应的现有玩法状态；强行显示会造成假接入或静默改变玩法。

因此，“把 PNG 加入 Xcode 包”只能证明文件可读取，不能证明游戏真正消费了它们。

## 3. 建议的核心运行时模型

### 3.1 资产描述符

每项正式资源最终应由一条类型化描述符管理，至少包含：

```text
assetKey -> filename -> nativeSize -> frameGrid -> anchor
         -> renderLayer -> gameplay/content state -> fallback -> evidence
```

原则：

- 代码使用稳定 `assetKey`，场景不直接散落字符串文件名。
- 像素运行层使用原生尺寸或整数倍缩放与 nearest-neighbor。
- 高清展示层保持原比例，不能替代地图碰撞、占格或交互数据。
- 角色 4×4 行走表按 `down / left / right / up`、每行 4 帧解释。
- 建筑按 `base / structure / roof / detail / interaction / state_fx` 组合，层级和锚点由数据明确给出。

### 3.2 语义渲染层级

建议集中为一个语义枚举，而不是各场景随手写 zPosition：

```text
ground < groundDetail < crop/propBase < buildingBase < actor
       < buildingOccluder < interactionFx < worldPrompt < hud < debug
```

### 3.3 HUD 状态

HUD 应从领域状态生成一个只读呈现快照，至少拆分为：

- 日期、时间段、天气、货币；
- 当前工具、目标格、可执行/不可执行原因；
- 快捷工具栏/背包摘要；
- 当前任务与暂存提示；
- 临时反馈（收获、出售、制作、错误）；
- 显式开启的调试数据。

调试字符串可以保留，但不能继续作为成品 HUD 的布局数据源。

## 5. 分批接入顺序

```text
B0 基础合同与审计
  └─ B1 农场地形 + 静态角色 + 紧凑 HUD（首个可玩垂直切片）
       └─ B2 集市地形 + 8 角色行走表
            └─ B3 作物/动作/采集/道具/FX
                 └─ B4 五建筑六层 + 5 张高清展示图
                      └─ B5 全路径视觉回归与 PO 截图验收
                           └─ N-016 正式音乐/环境/音效
```

每批必须保持可运行，禁止先删除全部回退再等待资源映射补齐。
