# 候选想法 Backlog

> 状态：治理记录，不是路线图或开发承诺。
> 负责人：🎬 director；独立质量复核：🛡️ quality。
> 依据：DEC-011、`docs/game/project-ledger.md`、R0-001。

## 目的与边界

本 Backlog 用来随时收集《溪谷新芽》的新想法，避免它们在未评估时改变已经批准的任务、依赖、范围或排期。记录一个想法只表示它值得保留，**不**表示它会被制作、排期、写入 PRD/TDD，或加入当前迭代。

只有完成影响评估并由 Product Owner 明确批准的候选，才可以创建新的台账任务或修改项目基线。

## 随时记录

记录时只要求填写“捕获字段”；未知项保持“待评估”，不得为了填满表格而编造结论。

| 字段 | 说明 |
|---|---|
| 想法 ID | 稳定 ID，格式 `IDEA-001`，只增不重用 |
| 捕获日期 | 记录日期 |
| 标题 | 简短、可区分的名称 |
| 想法描述 | 说明玩家、内容或制作流程会发生什么变化 |
| 预期价值 | 玩家体验、可玩性、可维护性或风险缓解的假设 |
| 影响面 | `design`、`content`、`tech`、`quality`、`production` 中的已知项；未知写“待评估” |
| 状态 | `captured`、`triage`、`evaluating`、`adopted`、`deferred` 或 `rejected` |
| 关联 | 相关 PRD/TDD、任务 ID 或“无”；关联不代表修改它们 |
| 决策记录 | 评估、批准或拒绝后链接对应台账决策与任务 |

## 评估与采纳流程

```text
captured → triage → evaluating → adopted / deferred / rejected
                                  ↓
                       Product Owner 明确批准
                                  ↓
                新建台账任务（planned）并完成依赖预检
```

1. **捕获**：任何时候可新增 `captured` 条目；不得同时改动路线图或现有任务。
2. **分诊**：仅在 Product Owner 明确要求评估、阶段退出门禁，或 R0-001 复盘时，将条目改为 `triage`。
3. **评估**：相关负责人分别记录下列事实，再设为 `evaluating`：
   - 🌱 `design`：玩家结果、核心循环、可用性与范围影响；
   - 🎭 `content`：原创性、内容预算与世界一致性；
   - 🧱 `tech`：架构、存档、性能、工具与依赖影响；
   - 🛡️ `quality`：验收、回归、无障碍与发布风险；
   - 🎬 `director`：节奏、优先级、前置条件与取舍。
4. **采纳**：只有 Product Owner 明确批准后，`director` 才能新建有稳定 ID、依赖和验收标准的 `planned` 台账任务；需要时同步更新 PRD/TDD，并在本条目填入链接。
5. **暂缓或拒绝**：保留原始想法、理由和日期，分别标记为 `deferred` 或 `rejected`；不得删除历史。

## 计划保护规则

- `captured`、`triage` 与 `evaluating` 条目不会改变当前任务状态、阶段状态、依赖、排期或验收标准。
- Backlog 条目不能绕过台账的依赖预检、部门门禁或 Product Owner 批准。
- 不将候选内容实现为游戏代码、场景、资产或配置；实现工作必须由获批的独立台账任务承载。
- 评估结论必须说明“采纳到哪个阶段、替换或新增什么、资源/风险影响是什么”；结论不充分时维持 `evaluating` 或 `deferred`。
- 想法必须保持原创；不得记录或采纳受保护角色、地图、对白、美术、音频、代码或其他可识别表达的复刻方案。

## 示例

**正向：** `IDEA-001` 记录“为水渠修复增加可选的季节性水位标记”。状态为 `captured`，影响面写 `design, content, tech`，关联写“无”。它不会改变 M0–M4 的任务或排期，直到正式评估。

**反向：** 在记录“新增宠物系统”后，直接修改 M1-001 的范围或开始制作宠物场景。该行为绕过评估、台账任务、依赖和 Product Owner 批准，不允许执行。
